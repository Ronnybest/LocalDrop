# LocalDrop — архитектура после смены продуктового курса

Статус: принято как целевая архитектура. Реализованное (Milestone 1–4) сохраняется там, где
подходит новой модели; изменения внедряются по плану из раздела 8.

## 0. Продукт в одном абзаце

LocalDrop — не приложение для передачи файлов, а **связь устройств**: Android и Mac ведут себя
как части одной экосистемы. Главный интерфейс — Android Sharesheet, уведомления macOS и
menu bar. Собственный экран LocalDrop нужен для первой привязки, управления устройствами,
настроек и диагностики. Метрика успеха: сколько действий исчезло у пользователя, и как редко
ему приходится открывать LocalDrop.

Эталонный сценарий:

```
Gallery → Share → MacBook Pro → (на Mac: уведомление или авто-приём) → Done
```

Каждое решение ниже проверяется двумя вопросами:

1. Уменьшает ли это количество действий пользователя?
2. Делает ли это связь Android и Mac похожей на системную возможность ОС?

---

## 1. Что в текущем дизайне слишком похоже на LocalSend

| Элемент | Почему это «LocalSend-паттерн» |
|---|---|
| Главный экран Android = «Nearby devices» + нажми на устройство, чтобы отправить | Классический LAN-sharing: открыл приложение → выбрал устройство → отправил. Ровно то, от чего уходим |
| Карточка «Test transfer» на главном экране | Отправка инициируется из нашего UI, а не из системы |
| Привязка происходит неявно, «по пути» при первой отправке | Устройство — побочный эффект отправки, а не постоянная сущность |
| Окно «X wants to send: Accept / Decline» на Mac как единственный путь | Аналог receive-диалога LocalSend; системные уведомления не используются |
| Каждое подключение начинается с чтения Endpoint Info по GATT | Discovery-ориентированная модель «нашли endpoint → передали» вместо «знакомое устройство рядом» |
| Статический `shortId` в BLE-рекламе | Любой рядом может отслеживать Mac и видеть, что это LocalDrop того же владельца; модель «виден всем» |
| Endpoint Info (имя, IP, порт, fingerprint) читается любым устройством рядом | То же: открытая витрина для незнакомцев |
| Bonjour `_localdrop._tcp` | Тот же механизм, что LAN-discovery конкурентов; у нас допустим только как fallback |

## 2. Что остаётся базовой инфраструктурой (без переписывания)

Эти части не являются отличием продукта, но они правильные, проверены на устройствах и
подходят новой модели:

- **Транспорт:** TCP, фрейминг `u32 length ‖ payload`, CBOR, версии протокола.
- **Криптография:** signed ephemeral ECDH (SIGMA), AES-256-GCM с неявными счётчиками,
  identity-ключи в Android Keystore / macOS Keychain, commitment + 6-значный код.
  Уже это и есть «persistent cryptographic pairing» — главное отличие от favorites.
- **Trust stores на обеих сторонах**, обнаружение смены ключа, немедленный отзыв доверия
  (`not_trusted` обрывает активные сессии).
- **Конвейер передачи:** чанки 256 KiB, потоковый SHA-256, временный файл → переименование
  после проверки, отказ по месту до запроса, отмена с обеих сторон, сторож зависаний.
  Замер: 105 MB/s через точку доступа телефона, предел сети через роутер.
- **`PeerConnector`:** обе топологии (общий Wi-Fi и точка доступа телефона), сокет никогда не
  уходит в мобильные данные.
- **BLE как механизм физической близости** (Mac — peripheral, Android — central): уже
  BLE-first, multicast не используется для поиска.
- **Явная модель состояний передачи** (`TransferState`), `TransferReceiver`, `SessionHandle`.
- **macOS menu bar agent** без основного окна.

## 3. Что меняется

| Область | Было | Станет |
|---|---|---|
| Точка входа Android | Главный экран со списком устройств | **Sharesheet**: Direct Share-цель на каждый доверенный Mac + цель «LocalDrop» как запасной путь |
| Владелец передачи на Android | `TransferManager` в application scope, жив пока жив процесс | **Foreground service** (`dataSync`), запускаемый из Share-цели; прогресс и результат — в уведомлении |
| Главный экран Android | Nearby devices + отправка тестовых данных | **Устройства**: доверенные Mac, «Добавить Mac», устройство по умолчанию, настройки. Тестовая передача уходит в «Диагностику» |
| Привязка | Неявно при первой отправке | **Явная операция «Добавить Mac»** (один раз), плюс неявная как fallback |
| Видимость Mac | Всегда виден всем | **Приватная реклама** для доверенных + **режим привязки** на ограниченное время (модель AirDrop «Contacts Only / Everyone for 10 minutes») |
| Endpoint Info | Открыт для всех | Зашифрован ключом присутствия; открыт только в режиме привязки |
| Поиск знакомого Mac | Всегда BLE → GATT → TCP | **Сначала последний известный endpoint** (TCP сразу) параллельно с BLE; GATT — только если не удалось |
| Приём на Mac | Плавающее окно | **Уведомление с действиями Accept/Decline**; окно — fallback, если уведомления выключены. Код привязки — всегда окно |
| Решение о приёме | Всегда спросить | **Политика по устройству**: Never / Ask / Photos only / Files under 100 MB / Always |
| Запись trusted device | id, имя, ключ, fingerprint, firstSeen, lastSeen (+platform на Mac) | + deviceType, capabilities, pairedAt, autoAcceptPolicy, isDefault, presenceKey, lastEndpoint |
| Протокол | Нет capabilities, нет присутствия | `caps` в hello, распределение ключа присутствия, флаг `busy` (раздел 5, 6) |

Переименовывать сообщения протокола ради «красивых» имён не будем. Текущие сообщения уже
описывают взаимодействие устройств, а не экраны:

| Понятие из стратегии | Сообщение v1 |
|---|---|
| DeviceHello / Capabilities | `client_hello` / `server_hello` (+ поле `caps`) |
| PairRequest / PairResponse | `session_status{pairing_required}` → `pairing_confirm` / `pairing_result` |
| TransferOffer / FileManifest | `transfer_request` (содержит manifest файлов) |
| TransferDecision | `transfer_accept` / `transfer_reject` |
| Chunk | `file_chunk` |
| TransferResult | `file_result` / `transfer_result` |
| Presence | BLE-токен + `presence_key` (новое) |

## 4. Direct Share для доверенного Mac на Android 11+

**API:** Sharing Shortcuts (API 29+). `ChooserTargetService` не используется: он объявлен
устаревшим в API 30.

Устройство:

1. `res/xml/shortcuts.xml` объявляет `<share-target>` с `targetClass = ShareTargetActivity`,
   категорией `dev.localdrop.category.SEND_TO_DEVICE` и MIME-типами `*/*` (+ `text/plain`).
   Подключается через `<meta-data android:name="android.app.shortcuts">` у активности,
   принимающей `ACTION_SEND` / `ACTION_SEND_MULTIPLE`.
2. `ShareShortcutPublisher` синхронизирует доверенные Mac с динамическими ярлыками:
   `ShortcutManagerCompat.pushDynamicShortcut(...)`, id ярлыка = `deviceId`, `setLongLived(true)`,
   `setCategories(SEND_TO_DEVICE)`, `setRank(0)` для устройства по умолчанию, иконка ноутбука.
   Срабатывает при привязке, «Forget», переименовании, смене устройства по умолчанию.
   После каждой успешной отправки — `reportShortcutUsed`, чтобы Android поднимал цель выше.
3. Нажатие на «MacBook Pro» в Sharesheet открывает `ShareTargetActivity` с
   `Intent.EXTRA_SHORTCUT_ID = deviceId` и `EXTRA_STREAM`/`EXTRA_TEXT`.
4. `ShareTargetActivity` — **прозрачная, без UI**: формирует запрос, передаёт URI в
   `TransferService` **вместе с грантом** (`ClipData` + `FLAG_GRANT_READ_URI_PERMISSION`;
   грант переходит к сервису и живёт, пока он работает), запускает foreground service
   (разрешено: активность на переднем плане) и сразу закрывается.
5. Дальше пользователь видит только уведомление с прогрессем и итогом.

Цель «LocalDrop» (обычная, не Direct Share) остаётся запасной:
- один доверенный Mac или задан Mac по умолчанию → отправка сразу, без выбора;
- несколько Mac → компактный bottom sheet только с доверенными устройствами + «Добавить Mac».

**Ограничения, которые нельзя обойти:**
- Порядок и количество Direct Share-целей в Sharesheet определяет система (ранжирование по
  использованию, лимит ярлыков на приложение ≈ 4–5). Гарантировать первую строку нельзя;
  `reportShortcutUsed` и устройство по умолчанию с `rank 0` — максимум, что доступно.
- Некоторые OEM-оболочки (MIUI/HyperOS и др.) заменяют системный Sharesheet и могут не
  показывать Direct Share. Там работает цель «LocalDrop» с мгновенной отправкой на Mac по
  умолчанию — на одно нажатие больше.
- Sharesheet не сообщает приложению, что он открыт, поэтому статус присутствия («рядом /
  нет») в подписи ярлыка не показываем: ярлык есть всегда, а присутствие проверяется после нажатия.

## 5. BLE presence

### Состояния (на Android, для каждого доверенного Mac)

| Состояние | Признак |
|---|---|
| `Offline` | Нет BLE-токена во время сканирования и последний endpoint не отвечает. Mac выключен, спит или далеко |
| `Nearby` | Свежий BLE-токен этого Mac (физически рядом и не спит) |
| `Reachable` | TCP до endpoint открылся (Mac в той же сети или в точке доступа телефона) |
| `Connected` | Аутентифицированная сессия открыта |
| `Busy` | Mac ответил `busy` (принимает другую передачу или идёт привязка) |

`Nearby` без `Reachable` — отдельная полезная диагностика: «Mac рядом, но в другой сети /
гостевая сеть блокирует соединения». Это знание даёт только BLE.

Присутствие вычисляется **по требованию** (нажатие на цель в Sharesheet, открытие приложения,
повтор из очереди), а не постоянно в фоне — так экономится батарея. Фоновое отслеживание
нужно только для очереди (раздел 8, фаза Queue).

### Приватная BLE-реклама (изменение протокола v1 до релиза)

Сейчас Mac рекламирует постоянный `LD` + `shortId` — отслеживаемый идентификатор. Новая схема:

- При привязке Mac передаёт телефону свой **ключ присутствия** `presenceKey` (32 байта,
  по зашифрованному каналу, сообщение `presence_key`). Ключ один на Mac; при «Forget» Mac
  генерирует новый и раздаёт оставшимся доверенным устройствам при их следующем подключении.
- **Приватный режим (по умолчанию):** local name = `L` + base64url(5 байт), где
  5 байт = первые байты `HMAC-SHA256(presenceKey, "localdrop/v1/presence" ‖ u64 slot)`,
  `slot = floor(unixTime / 900)`. Токен меняется каждые 15 минут; телефон проверяет слоты
  `slot−1..slot+1` (допуск на расхождение часов). Посторонний видит только случайные байты.
- **Режим привязки:** local name = `P` + 6 hex `shortId`. Включается из menu bar
  («Добавить устройство…») на 10 минут, а также автоматически, пока доверенных устройств нет.
- **Endpoint Info** в приватном режиме шифруется AES-GCM ключом, производным от
  `presenceKey`; в режиме привязки — открыт, как сейчас.
- macOS позволяет рекламировать только local name и service UUID — поэтому токен живёт в
  имени (8 символов), а не в manufacturer data.

Токен — подсказка «этот Mac рядом», а не доказательство личности: подлинность по-прежнему
подтверждается подписью в handshake.

### Быстрый путь подключения

После нажатия «MacBook Pro» параллельно:
1. TCP к `lastEndpoint` (последние адреса и порт этого Mac);
2. BLE-скан до совпадения токена → при необходимости чтение Endpoint Info.

Побеждает первый успешный handshake. В знакомой сети отправка стартует без ожидания BLE.

## 6. Persistent pairing

Привязка — **отдельная операция**, выполняемая один раз:

1. На Mac: menu bar → «Добавить устройство…» (режим привязки на 10 минут). Если доверенных
   устройств нет, режим включён сам.
2. На Android: LocalDrop → «Добавить Mac» → Mac в режиме привязки рядом → нажать.
3. Оба экрана показывают один код (уже реализовано) → подтверждение на обоих.
4. Mac передаёт `presence_key` и `caps`; обе стороны сохраняют запись; Android публикует
   Direct Share-ярлык. С этого момента приложение больше не нужно для отправки.

Неявная привязка при первой отправке остаётся как fallback (уже работает).

Запись доверенного устройства (обе платформы; поля, не имеющие смысла на стороне, пустые):

```
deviceId           UUID устройства
deviceName         отображаемое имя (обновляется при подключении)
deviceType         phone | tablet | laptop | desktop
platform           android | macos
publicKey          identity key, X9.63
fingerprint        SHA-256(publicKey)
pairedAt           дата привязки (не путать с lastSeen)
lastSeen           последняя аутентифицированная сессия
capabilities       [files, multipleFiles, text, clipboardReceive, clipboardSend, delayedTransfer, autoAccept, presenceToken]
presenceKey        (Android) ключ присутствия Mac
lastEndpoint       (Android) адреса, порт, время
isDefault          (Android) Mac по умолчанию
autoAcceptPolicy   (Mac) never | ask | photosOnly | under100MB | always — для этого телефона
textToClipboard    (Mac) класть полученный текст в буфер обмена
```

Это trusted device, а не favorite: запись существует только после взаимного
криптографического подтверждения, смена ключа не принимается молча, «Forget» отзывает доступ
немедленно.

Без private API, без accessibility-хаков, без отключения защиты.

## 8. Новый MVP и план работ

### Definition of MVP

1. Android и Mac один раз проходят pairing.
2. Mac сохраняется как trusted device.
3. Mac работает без открытого окна (menu bar, запуск при входе).
4. Android обнаруживает Mac поблизости (BLE-токен / последний endpoint).
5. Mac — прямая цель в Sharesheet (Direct Share), либо цель «LocalDrop» с мгновенной
   отправкой на Mac по умолчанию там, где OEM скрывает Direct Share.
6. Пользователь выбирает файл в любом приложении.
7. Share → MacBook Pro.
8. Mac получает запрос (уведомление или авто-приём по политике).
9. Передача по LAN.
10. Основной UI LocalDrop не открывался.

### План (заменяет Milestone 5–8)

| Milestone | Содержание | Что исчезает у пользователя |
|---|---|---|
| **5. Share to Mac** | `ShareTargetActivity` без UI, Direct Share-ярлыки доверенных Mac, `TransferService` (foreground, уведомления), `content://` (один и несколько файлов), текст. Mac: уведомления Accept/Decline, «Получено», запуск при входе. Главный экран Android → «Устройства», тестовая передача → «Диагностика» | Открытие LocalDrop, поиск и выбор устройства, кнопка Send |
| **6. Presence** | Модель присутствия, приватный BLE-токен + режим привязки, `presence_key`, `caps` в hello, mDNS как третий путь поиска | Mac больше не виден посторонним; понятный статус «рядом / в другой сети / спит» |
| **7. Policies** | `autoAcceptPolicy` на Mac, Mac по умолчанию на Android, текст → буфер обмена Mac, Quick Settings-плитка «Буфер обмена → Mac» | Нажатие Accept на Mac; выбор Mac при отправке |
| **8. Queue** | Отложенная отправка: spool, повтор при появлении Mac | Повторная отправка вручную, если Mac спал |

После каждого milestone — короткий product review по четырём вопросам: что стало быстрее,
что происходит автоматически, какие действия исчезли, что LocalSend делает почти так же.

### Задел под очередь уже в Milestone 5 (чтобы не переписывать)

- Передача описывается персистентной записью `OutgoingTransfer` (id, deviceId, список
  источников, статус), а не только состоянием в памяти. В M5 записи живут в памяти и
  завершаются сразу; в M8 те же записи сохраняются на диск.
- `TransferSource` уже абстрагирует источник; в M8 добавляется `SpooledSource`
  (копия в приватном каталоге), так как грант на `content://` временный.
- `transferId`/`fileId`/`offset` в протоколе уже есть — продолжение после обрыва ложится
  на них без изменения транспорта.

### Product review: уведомления о передаче на Android

- **Было:** одна строка «файл · 243 МБ из 1,0 ГБ · 27 МБ/с · осталось ≈ 30 с», в заголовке
  «Отправка на …», прогресс в чипе — проценты.
- **Стало:** в шапке направление и Mac («→ MacBook Pro», «← MacBook Pro»), в заголовке что
  передаётся, одна строка о главном («Осталось ≈ 30 с · файл 2 из 3», «Ждёт ответа на Mac»);
  скорость — на экране передачи.
- **Live Update (Android 16):** чип «30 с» / «2 мин», округлённо вверх; полоса и точка-бегунок
  в цветах системной темы, по отрезку на файл (до 10 файлов); в конце полосы — только
  устройство-получатель (ноутбук или телефон, дальше — любая платформа). Закреплён с первого
  шага: ожидание Mac не уходит в «Без звука». Волнистую полосу в уведомлении рисует только
  система — у приложения её нет; она будет на экране передачи (Material 3 Expressive).
- **Итог:** имя или «3 файла», «Сохранено в «Загрузки»», миниатюра фото и «Поделиться»;
  «Отправлено · 1 ГБ за 38 с»; ошибки красным. Проверено на Pixel 8 (Android 16).

### Product review Milestone 9 (Mac → телефон)

- **Быстрее:** файл с Mac на телефоне без единого действия на телефоне, кроме «Принять» (или
  совсем без них для Mac с автоприёмом). Телефон замечает файлы и подключается за 0,3–5 с при
  включённом экране (около минуты при выключенном — так система доставляет результаты скана во
  сне). 100 MB — 3,5 с: 28–34 MB/s в обе стороны по одной сети 5 ГГц.
- **Способы отправить с Mac:** начать тащить файлы — у края экрана появляются телефоны;
  «Поделиться → LocalDrop» в Finder, «Фото», Safari (ссылка) и для выделенного текста; ✈ и
  правый клик на телефоне в меню («Отправить файлы…», «Отправить буфер обмена»). Папки уходят
  zip-архивом без сжатия (`ditto`, как «Сжать» в Finder): 1 ГБ упаковывается за доли секунды,
  а сжатие шло ~85 МБ/с — втрое медленнее сети. Упаковка видна в меню и на значке, её можно
  отменить; файлы, которые macOS не даёт прочитать (метка другого приложения), пропускаются.
- **Автоматически:** телефон просыпается сам — системный BLE-скан с `PendingIntent` будит
  приложение, даже закрытое; сигнал адресован одному телефону (метка в Pending Delivery UUID,
  §2.8), остальные не подключаются. Очередь Mac переживает перезапуск и ждёт телефон до недели.
  Текст и ссылки идут в буфер обмена в обе стороны; принятые на Mac файлы — в буфер обмена Mac
  (⌘V в чат). Прогресс на Android 16 — Live Update в строке состояния; везде — оставшееся время.
- **Исчезли действия:** открыть LocalDrop на телефоне, чтобы принять; кабель, облако или чат с
  собой для пути Mac → телефон; копировать принятое фото руками, чтобы вставить его в чат.
- **Как у LocalSend:** у них получатель должен держать приложение открытым и видимым; файлы
  не ждут, пока получатель появится; сигнала «есть файлы для тебя» нет.
- **Ограничения платформ, описаны честно:**
  - Запускать приём из фона Android 12+ разрешает приложению с привязкой Companion Device
    Manager. Пользователь подтверждает её один раз, системное окно говорит общими словами
    («например имя того, кто вам звонит»), поэтому карточка до него объясняет, что привязка
    даёт и чего не даёт, и предлагает «Позже»; отвязать можно в меню Mac. Без неё приём
    начинается по нажатию на уведомление.
  - Bluetooth-имя Mac — сменяемый токен; переименование в окне привязки должно сохранить хотя
    бы один его символ, а префикс — не длиннее 10 символов: отсюда «LocalDrop · MacBook Pro».
  - Расширение «Поделиться» включает только пользователь; меню и настройки Mac ведут прямо к
    переключателю, пока оно выключено.
  - APK ставит установщик только из приложения с правом установки; LocalDrop его не просит —
    уведомление открывает «Загрузки», и APK ставит «Файлы».
  - Тащить файлы к строке меню неудобно: у верхнего края macOS открывает Mission Control.
    Поэтому цели приходят к файлам — панель у края экрана, — а капля в строке меню файлы не
    принимает.
- **Найдено на устройствах и что из этого стало:**
  - `NWConnection` отдавал телефону 10–19 MB/s там, где сокет ядра — 22–35 (одинаковые
    условия, попеременные замеры): транспорт Mac переведён на BSD-сокеты и `DispatchIO`.
  - Скан пробуждения в режиме low-latency при открытом LocalDrop делил радио с Wi-Fi и срезал
    приём до 10 MB/s: скан — low-power, пробуждение осталось секундным.
  - `CALLBACK_TYPE_FIRST_MATCH` на Pixel срабатывал через раз: все совпадения плюс свой
    15-секундный фильтр повторов.
  - Android отбрасывает обновления уведомлений чаще ~5 раз в секунду: прогресс — раз в секунду.
  - Android 16 сворачивал запрос в пачку с результатами и прятал «Принять»/«Отклонить»: у
    запроса своя группа со сводкой, и он стоит на месте служебного уведомления, а не рядом.
  - MediaStore ставит « (1)» после неизвестного расширения («a.bin (1)»), а Mac присылает
    `octet-stream` для типов, которых не знает macOS (.apk): тип берётся по расширению, номер
    переносится перед ним.
  - Своя панель меню с Liquid Glass падала (рекурсия при изменении размера окна) и требовала
    вручную повторять поведение системного меню: вернулись к `MenuBarExtra`.
  - Короткие ночные пробуждения Mac (~120 за ночь) каждый раз перечитывали сеть: теперь только
    при настоящем пробуждении.
  - Safari при выделенном тексте отдаёт расширению выделение вместо страницы — уходит текст;
    ссылка — когда на странице ничего не выделено.
- **Проверяемость:** `protocol/test-vectors.properties` проверяют тесты обеих платформ —
  ключи рукопожатия, кадры, код привязки, отпечаток, токен, метка доставки, Endpoint Info.

### Product review Milestone 8

- **Быстрее:** отправка на спящий Mac больше не требует повторять её вручную: телефон
  сохраняет копию (78 MB — 1,4 с) и отправляет сам, как только Mac проснулся и рядом.
- **Автоматически:** ожидание и повтор (BLE-токен Mac со статусом `L`, смена сети, редкий
  таймер); всё, чем поделились на один Mac, уходит одной передачей — одно окно на Mac; пока
  окно открыто, новые файлы добавляются в него (`transfer_add`, `fileCount` в ответе).
- **Батарея Mac:** каждая сетевая попытка будит спящий Mac (macOS просыпается на входящее
  соединение). Пока у телефона работает Bluetooth, повтор ждёт рекламы Mac — он начинает её,
  только реально проснувшись; таймер — подстраховка раз в 5–15 мин. Скан первые 5 минут
  ожидания low-latency (balanced пропускал проснувшийся Mac 20+ с), потом balanced с
  перезапуском каждые 10 мин (Android делает 30-минутный скан opportunistic).
- **Исчезли действия:** «не отправилось — открыть галерею и поделиться ещё раз».
- **Как у LocalSend:** у них отправка на недоступное устройство просто падает; очереди нет.
- **Ограничение Android, описано честно:** фоновое приложение не может само снова запустить
  foreground service, поэтому ожидание в фоне ограничено часом (и суточным лимитом `dataSync`
  на Android 15). Дальше отправка «припаркована»: уведомление «Try again», повтор при открытии
  LocalDrop и при любой новой отправке. Следующий шаг без хаков — user-initiated data transfer
  jobs (Android 14+), которые система сама запускает при появлении сети.
- **Найдено на устройствах:** при закрытой крышке macOS в фоновых пробуждениях отвечает по
  сети, и запрос попадал в окно, которое никто не видит — теперь Mac отвечает `asleep` и
  телефон ждёт. Скан в режиме low-power на Mi A2 не замечал проснувшийся Mac 20+ с — для
  ожидания используется balanced.

### Product review Milestone 7

- **Быстрее:** фото из галереи сохраняется на Mac без единого нажатия на Mac (политика
  «Photos and videos»): от «Поделиться» до файла в Downloads — 0,3 с для 1 MB. Текст — одно
  сообщение, без вопроса, сразу в буфер обмена Mac.
- **Автоматически:** решение о приёме по политике устройства; ссылка в буфере как URL;
  Mac по умолчанию первым в Sharesheet и для плитки.
- **Исчезли действия:** Accept на Mac для разрешённых типов; сохранение текста в файл и
  копирование из него; выбор Mac при отправке с плитки или из цели «LocalDrop».
- **Как у LocalSend:** у них авто-приём — один переключатель на всё приложение, без
  привязки к проверенному устройству и типу файлов; текст не попадает в буфер обмена сам.
- **Безопасность:** политика применяется только к устройству с проверенной подписью и тем же
  ключом; «фото» — только если и MIME, и расширение итогового имени — изображение или видео;
  ссылки никогда не открываются сами; по умолчанию — «спрашивать».
- **Найдено на устройствах:** Telegram не показывает `PROCESS_TEXT` в своём меню выделения.

### Product review Milestone 6

- **Быстрее:** статус Mac на телефоне меняется за 2–8 с (ушёл / уснул — 8 с без рекламы;
  «занят → готов» — по статус-букве, без GATT-чтения). Уже привязанный Mac в режиме
  привязки узнаётся по короткому id мгновенно, без подключения. Зависшее GATT-подключение
  обрывается через 5 с и сразу повторяется.
- **Автоматически:** телефон сам отличает «рядом и в нашей сети», «рядом, но в другой сети»,
  «рядом, но без сети», «занят». Mac сам переключается между приватным режимом и режимом
  привязки, прячется во сне, меняет токен каждые 15 мин.
- **Исчезли действия:** отправка «вслепую» на спящий или чужой по сети Mac — статус виден
  до нажатия. Посторонним Mac больше не виден: включать видимость нужно только для новой привязки.
- **Как у LocalSend:** их устройства видны всем в сети постоянно; статуса «рядом, но в
  другой сети» нет — устройство просто отсутствует в списке.
- **Найдено на устройствах:** первое GATT-подключение после перезапуска рекламы Mac часто
  зависает (Mi A2) — неудачное чтение повторяется через 3 с и не сбрасывает последний
  известный адрес; Wi-Fi «без интернета» — честное оранжевое состояние в меню Mac.

### Product review Milestone 5

- **Быстрее:** Галерея → Поделиться → MacBook Pro. Запрос появляется на Mac через 0,2–0,3 с
  после нажатия (прямое подключение по последнему endpoint; Bluetooth нужен только для
  первой привязки и как запасной путь).
- **Автоматически:** Mac — прямая цель Sharesheet; передача живёт в foreground service
  (заблокированный экран, свёрнутое приложение); итог — уведомлением; запуск при входе.
- **Исчезли действия:** открыть LocalDrop, искать и выбирать устройство, нажимать Send.
  Остался Accept на Mac — его снимают политики auto-accept (M7).
- **Как у LocalSend:** у них нет Mac-цели в Sharesheet и нет постоянной криптографической
  связи устройств — отправка начинается в их приложении.
- **Перенесено из M6 в M5 по факту тестов:** быстрый путь через `lastEndpoint` и
  постоянный порт Mac — без них отправка зависела от нестабильного BLE GATT.
- **Найдено на устройствах:** App Nap делает Bluetooth-сессию агента «неактивной»;
  баннеры уведомлений macOS прячут кнопки до наведения — запрос стал собственной плашкой.

### Product review Milestone 1–4

- **Быстрее:** передача 1 GB — 9.5 с через точку доступа телефона; выбор маршрута автоматический.
- **Автоматически:** повторное подключение без кода, проверка целостности, отказ при нехватке места.
- **Исчезли действия:** повторный pairing, ручная проверка файла.
- **Как у LocalSend:** список устройств + отправка из своего приложения — именно это
  заменяет Milestone 5.

## 9. Технические риски нового UX

| Риск | Следствие | Что делаем |
|---|---|---|
| Ранжирование Direct Share — у системы | Mac может оказаться не в первой строке | `reportShortcutUsed`, rank 0 для Mac по умолчанию; цель «LocalDrop» с мгновенной отправкой |
| OEM-оболочки без Direct Share | Нет прямой цели | Та же цель «LocalDrop», +1 нажатие; фиксируем список проверенных оболочек |
| Грант на `content://` временный | Отложенная отправка не прочитает файл | Передавать грант сервису; для очереди — spool с лимитом размера и явным отказом для огромных файлов |
| Запуск foreground service из фона запрещён с Android 12 | Очередь не стартует сама в фоне | M5: старт только из Share-активности (разрешено). M8: CompanionDeviceManager (API 31+ — исключение для старта из фона; API 33+ — self-managed связь) либо уведомление «Mac рядом — отправить?». Android 14+: user-initiated data transfer jobs. Android 15: лимит 6 ч на `dataSync` |
| Фоновое BLE-сканирование ограничено | Присутствие в фоне неточное | Сканирование по требованию; для очереди — скан с фильтром через `PendingIntent` |
| Android 11: скан требует геолокацию и включённый Location | Без них нет `Nearby` | Быстрый путь через `lastEndpoint` работает без BLE; понятная подсказка |
| Mac спит — BLE и сеть недоступны | `Offline` | Честный статус + очередь (M8); будить Mac не пытаемся |
| macOS-реклама — только local name (8 символов) | Мало места под токен | 40-битный токен, ротация 15 мин, допуск ±1 слот на часы |
| Расхождение часов телефона и Mac | Токен не совпал | Проверка 3 слотов (±15 мин); fallback — `lastEndpoint` и GATT |
| Уведомления macOS выключены или стиль «баннеры» | Accept/Decline скрыты | Проверка авторизации; fallback — окно; подсказка в меню |
| Auto-accept от скомпрометированного устройства | Нежелательные файлы сохраняются сами | Только для trusted с проверенной подписью, по умолчанию Ask, opt-in на устройство, карантин Gatekeeper, никогда не открывать автоматически |
| Ротация `presenceKey` после «Forget» | Оставшиеся телефоны временно не узнают Mac по BLE | Fallback на `lastEndpoint`/GATT; новый ключ при следующей сессии |
| App Nap на macOS «усыпляет» агента без окон, и Bluetooth-стек отказывает в GATT-чтении (`inactive session`): Mac виден, но не отвечает | Отправка падает с «not nearby» | **Подтверждено и исправлено в M5:** агент держит `beginActivity(.userInitiatedAllowingIdleSystemSleep)` — App Nap выключен, сон системы разрешён. M6 добавляет путь без GATT (последний endpoint, mDNS) |
| Буфер обмена Android в фоне недоступен (Android 10+) | Нет авто-синхронизации буфера | Только явные действия: Share текста, плитка, открывающая прозрачную активность, «Send to Mac» в меню выделения (`PROCESS_TEXT`). **Подтверждено в M7:** приложения со своим меню выделения (Telegram) `PROCESS_TEXT` не показывают — там «Копировать» → плитка |
