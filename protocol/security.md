# LocalDrop Protocol v1 — безопасность

## 1. Модель угроз

Защищаемся от:

* пассивного прослушивания Wi-Fi/BLE;
* активного MITM в локальной сети (ARP/DNS spoofing, поддельный BLE advertisement);
* подмены устройства после первой привязки;
* повтора и переупорядочивания фреймов.

Не защищаемся (вне scope v1): скомпрометированная ОС устройства, DoS в локальной сети,
анализ трафика (размеры/тайминги).

## 2. Ключи

| Ключ | Алгоритм | Где живёт | Срок жизни |
|------|----------|-----------|------------|
| Identity key | ECDSA P-256 | Android Keystore (non-exportable) / macOS Keychain | постоянный |
| Ephemeral key | ECDH P-256 | память процесса | одна сессия |
| Session keys | AES-256-GCM | память процесса | одна сессия |

Почему P-256, а не Ed25519/X25519: Android Keystore на Android 11 поддерживает только
EC P-256 для подписи (Ed25519 в Keystore нет). ECDH-agreement в Keystore появился только
в Android 12 (API 31), поэтому ephemeral ECDH делается системным JCA-провайдером в памяти —
это нормально, ключ одноразовый.

Почему не TLS: TLS с взаимной аутентификацией требует X.509-сертификатов на обеих сторонах.
На macOS нет системного API для выпуска самоподписанного сертификата, а SecIdentity
из CryptoKit-ключа собрать нельзя без ручного DER. Протокол ниже — стандартная
схема SIGMA (signed ephemeral Diffie–Hellman) из системных примитивов:
ECDH, ECDSA, HKDF, AES-GCM. Ни один криптографический алгоритм не реализуется вручную;
HKDF (RFC 5869) на Android собирается из системного `HmacSHA256`, т.к. платформа не
предоставляет HKDF напрямую.

* `deviceId` — случайный UUID, генерируется при первом запуске, хранится отдельно от ключа.
  Это позволяет обнаружить смену ключа у известного устройства.
* `fingerprint = SHA-256(identityPublicKey_X963)` — внутренний идентификатор ключа (BLE,
  Bonjour, логи по префиксу); пользователю не показывается.
* **Код проверки пары** — то, что пользователь сверяет на обоих устройствах в любой момент
  после привязки (в отличие от SAS, который живёт одну сессию):
  `h = SHA-256("localdrop/v1/verify" ‖ min(pkA, pkB) ‖ max(pkA, pkB))`, где `pk` — identity
  public keys X9.63, а `min`/`max` — побайтовое сравнение; код = `uint64_BE(h[0..8]) mod 10¹²`,
  12 цифр с ведущими нулями, группами по 4: `9854 2474 7763`. Одинаков на обеих сторонах,
  меняется, если ключ любой из них сменился.

## 3. Handshake

```
CH  = client_hello{ idKey_C, eph_C, nonceCommit = SHA-256(nonce_C) }
SH  = server_hello{ idKey_S, eph_S, nonce_S }
CN  = client_nonce{ nonce_C }

th  = SHA-256( frame(CH) ‖ frame(SH) ‖ frame(CN) )      // frame = u32 length ‖ payload, байты как на проводе

ss      = ECDH(eph_C, eph_S)                             // 32 байта, X-координата
k_c2s   = HKDF-SHA256(ikm=ss, salt=th, info="localdrop/v1/c2s", L=32)
k_s2c   = HKDF-SHA256(ikm=ss, salt=th, info="localdrop/v1/s2c", L=32)
sasBits = HKDF-SHA256(ikm=ss, salt=th, info="localdrop/v1/sas", L=4)

server_auth.sig = ECDSA_Sign(id_S, "localdrop/v1/server-auth" ‖ th)
client_auth.sig = ECDSA_Sign(id_C, "localdrop/v1/client-auth" ‖ th)
```

* Initiator проверяет `server_auth` до отправки `client_auth`.
* Responder проверяет `SHA-256(nonce_C) == nonceCommit`, затем `client_auth`.
* Любая ошибка проверки → `error{auth_failed}` и закрытие.
* `eph` — валидная точка кривой (проверяется системным API при импорте).

### Commitment

Initiator коммитится к `nonce_C` до того, как увидит параметры Responder'а, и раскрывает
его после. Responder выбирает `nonce_S`/`eph_S`, не зная `nonce_C`. Поэтому MITM не может
перебором подобрать свои ephemeral-ключи так, чтобы 6-значные коды в двух сессиях совпали —
вероятность успеха одной попытки 10⁻⁶, и каждая попытка — новая привязка, видимая пользователю.

## 4. Шифрование фреймов

* AES-256-GCM, отдельный ключ на каждое направление.
* Nonce (12 байт) = `0x00000000 ‖ counter_u64_BE`. Счётчик стартует с 0 для каждого
  направления, увеличивается на 1 после каждого фрейма и **не передаётся** — повтор,
  удаление или переупорядочивание фрейма ломает проверку тега.
* AAD пустой (длина фрейма аутентифицируется косвенно через тег и счётчик).
* Ошибка дешифрования → `decrypt_failed`, соединение закрывается без повторов.
* Переполнение счётчика (2⁶⁴) невозможно на практике; реализация всё равно закрывает
  сессию при достижении предела.

## 5. Привязка (pairing)

1. `session_status` = `pairing_required` или `key_changed`.
2. Обе стороны показывают код `SAS = (uint32_BE(sasBits) mod 1 000 000)`, 6 цифр
   с ведущими нулями, формат `481 273`, и имя peer'а.
3. При `key_changed` дополнительно показывается предупреждение:
   «Ключ устройства изменился. Это может быть переустановка приложения — или подмена.
   Продолжайте, только если устройство у вас в руках.»
4. Пользователь Initiator'а → `pairing_confirm{accepted}`.
5. Responder ждёт решения своего пользователя, отвечает `pairing_result{accepted = оба true}`.
   Если его пользователь отклонил раньше — отвечает `false` сразу (см. `messages.md`).
6. При успехе обе стороны сохраняют peer (заменяя старый ключ при `key_changed`).

Responder допускает одну одновременную привязку (остальные → `busy`) и не более 5 попыток
привязки в минуту.

## 6. Trusted devices

Запись:

```
deviceId, deviceName, publicKey (X9.63), fingerprint, firstSeen, lastSeen
```

* Статус сессии вычисляет Responder: `key_changed`, если хотя бы одна сторона видит смену
  ключа (`client_auth.keyChanged` или своё хранилище); `trusted` — только если **обе**
  стороны доверяют текущим ключам (`client_auth.trusted` и своё хранилище); иначе
  `pairing_required`. Доверие одной стороны не даёт доступа без доверия другой.
* Android: файл в `noBackupFilesDir` (не уходит в бэкап/на другие устройства).
* macOS: Application Support внутри sandbox-контейнера.
  Публичные ключи не секретны; секретом является только identity private key.
* Смена ключа у известного `deviceId` **никогда** не принимается молча.
* Пользователь может удалить устройство из trusted. Это **немедленно** завершает все активные
  сессии с ним (`error{not_trusted}`, незавершённый файл удаляется), а следующее соединение
  потребует привязки. Отзыв доверия отзывает и уже выданный доступ.

## 6a. Ключ присутствия

* `presenceKey` — 32 случайных байта Responder'а, хранится в Keychain. Передаётся доверенным
  устройствам только внутри зашифрованного канала (`session_status`, `pairing_result`).
* Даёт право **узнать** Responder по BLE-токену и прочитать запечатанный Endpoint Info.
  Не даёт права подключиться: доступ по-прежнему требует подписи trusted identity key.
* При «Forget» Responder генерирует новый ключ: удалённое устройство перестаёт узнавать его
  по BLE. Оставшиеся получают новый ключ при следующей доверенной сессии.
* Режим привязки (10 минут или пока нет доверенных устройств) — единственное время, когда
  Responder узнаваем посторонними и принимает сессии, требующие привязки.

## 7. Что никогда не логируется

Содержимое файлов, приватные ключи, session keys, shared secret, `sasBits` и сам SAS-код,
nonce'ы, ключ присутствия. Fingerprint в логах — первые 8 hex-символов.

## 8. Авторизация передач

* `transfer_request` принимается только в сессии со статусом `trusted` или после
  успешного `pairing_result` в этой же сессии; иначе `error{not_trusted}`.
* Каждая входящая передача требует явного Accept от пользователя получателя,
  даже от trusted-устройства.
* Имя файла санитизируется получателем: удаляются `/`, `\`, `:`, управляющие символы,
  ведущие точки; пустое имя → `file`; при коллизии добавляется ` (n)`.
